    Decision Frame

    This sprint is intentionally breadth-first. We are shipping visible screens before cross-cutting systems, then using one explicit rule to keep the retrofit day survivable.

    The Bet

    Visible Progress First, Retrofit Risk Later

    The chosen sequence is not the safest one. It is the one most likely to make the product feel real fastest: polish the visible surfaces on Days 1 and 2, then layer Dark Mode and the celebrations primitive across them on Day 3.

    Safer Alternative

    Front-load systems, reduce retrofit exposure

    A conservative sequence would lock down tokens and reusable primitives earlier, then add or polish screens once the foundation was stable.

    • Lower risk of late regressions
    • Less chance of a retrofit scramble on Wednesday
    • Slower visible momentum during the sprint
    Chosen Sequence

    Screens first, systems last

    The sprint is optimized for demonstrability. By the end of Day 2, the core post-onboarding journey should already feel traversable, even before the system pass lands.

    • Fastest path to believable progress
    • Real screens create better retrofit targets
    • Requires discipline around tokens and scope

    Sequence

    Three Days, One Runway

    The day-by-day plan deliberately matches the seven-item scope with no floating “refinement” bucket. The first two days produce surfaces. The third day makes them system-ready and shippable.

    The order matters: the system work is intentionally last, but only because earlier code is constrained to tokens from the start.
    Boundaries

    Cuts Are Global. Unknowns Stay Local.

    The sprint stays credible by cutting vague work entirely and by pushing unresolved implementation questions down into the sub-projects that actually own them.

    What left the sprint

    Anything with no crisp output got removed instead of becoming a hidden drain bucket.

    Refinements cut Game Details excluded
    • Refinements had no concrete list, so it was cut rather than treated as spare-capacity filler.
    • Game Details Screen was removed because it already exists in Flutter and in the extracted Figma work.

    What gets decided later

    Data-shape and pattern choices only defer if they belong to a specific item and can be resolved inside that item’s own brainstorm, spec, and plan.

    Transaction History source Streaks data model Polish redesign questions
    • Transaction History can derive from journeyLog or a new ledger, but the sprint doc does not pretend to settle that centrally.
    • Streaks View owns its own state contract in the same way.
    • Polish items stay in verify-and-tighten mode; redesign-scale discoveries are timeboxed or cut.
    Guardrails

    One Rule Keeps Day 3 From Becoming a Death March

    The retrofit day only works if the earlier work is done under constraint. The sprint inherits an existing project convention and treats it as a hard survival rule for the week.

    The survival rule

    No new hardcoded hex codes enter the codebase during the sprint. Every color used in new work routes through token definitions in flutter_app/lib/theme/app_theme.dart.

    No new hardcoded hex codes. Every color in new code this week goes through AppColors tokens.

    That turns Dark Mode from a repo-wide grep exercise into a token expansion job. It is also aligned with the existing convention established in commit 8cd5385, so the sprint is enforcing discipline, not inventing a new rule under pressure.

    Risk 1

    Retrofit panic

    Mitigation: enforce tokens on Days 1 and 2 so Day 3 only adds values rather than replacing literals.

    Risk 2

    Data-source ambiguity

    Mitigation: resolve Transaction History and Streaks data contracts during each screen’s own brainstorm instead of faking certainty here.

    Risk 3

    Scope creep on polish

    Mitigation: keep Home and Wallet framed as verification and tightening work, not quiet redesign exercises.

    Risk 4

    Celebration regressions

    Mitigation: build and test the reusable primitive in isolation before migrating existing Wallet payout flow callers.

    Cadence

    Seven Small Projects, One Repeated Loop

    The sprint is not one giant implementation ticket. Each item gets a contained brainstorm, spec, plan, and implementation pass, starting with Post-Onboarding Home polish.

    1

    Brainstorm

    Resolve only the question the item actually owns, usually around pattern choice rather than product definition.

    2

    Design Doc

    Write the item-specific spec into docs/superpowers/specs/2026-04-13-<name>-design.md.

    3

    Plan

    Create the paired implementation plan in docs/superpowers/plans/2026-04-13-<name>.md.

    4

    Implementation

    Ship the item, then move to the next one with the same loop instead of letting unresolved questions accumulate.

    The value of the sprint is not that every surface feels finished. It is that by Thursday, the post-onboarding story is no longer theoretical: it can be walked, tested, and reacted to as a complete loop.
